Cloudflare上にSera Protocol専用のフルサーバーレスAIチャットボットを構築し、その実装を解説する日本語の技術ブログを執筆したいです。

このターンでは実装を開始せず、既存ソースコードと公式ドキュメントの調査、要件整理、設計、実装計画の作成を行ってください。
コード変更、クラウドへのデプロイ、オンチェーン取引は行わないでください。

単なるタスク一覧ではなく、計画の合意後に実装へ進める具体性を求めています。

## 1. プロジェクトの目的

テーマ：
「Cloudflare WorkersとPagesで構築する、フルサーバーレスなSera AI Agent」

成果物は次の3つです。
1. 実際に動作するサンプルアプリ
2. 読者が環境構築・デプロイ・動作確認・削除まで再現できるREADME
3. 設計判断と主要な実装を解説する日本語の技術ブログ原稿

想定読者は、TypeScriptとReactの基礎は理解しているが、
Cloudflare Workers、AI Agent、MCP、Sera Protocolには詳しくない開発者です。

教材としての分かりやすさ、再現性、低コスト、保守性を重視してください。

既存のAWS版や関連コードがある場合は調査対象に含め、
共通化できるドメイン処理とCloudflare固有の実装を整理してください。
ただし、AWS版の存在を仮定したり、既存コードを上書きしたりしないでください。

## 2. 実現したい機能

ユーザーがWebのチャット画面から自然言語で以下を操作できるようにします。

- ウォレットの作成
- ウォレットの残高確認
- Sera Protocolの板・取引情報の取得
- ステーブルコインのswap
- 送金
- 実行結果とトランザクション状態の確認

必要な入力が不足している場合は、チャットで補完します。
読み取り操作と資産を変更する操作は区別してください。

swap・送金は、対象ネットワーク、トークン、数量、送信先、
手数料やスリッページなどの必要情報を確認画面に表示し、
ユーザーの明示的な承認後に実行する設計にしてください。

LLMの文章だけで取引成功を判定せず、
ツールの実行結果とチェーン上の状態を根拠に表示してください。

## 5. Workers互換性の検証計画

Workersを一般的なNode.jsサーバーと同一視しないでください。
nodejs_compatの設定だけで全依存ライブラリが動くと判断しないでください。

次の項目について、ソースと現行の公式資料を確認してください。

- Strands TypeScript SDKとモデルプロバイダーの実行環境要件
- MCPクライアント・サーバーの対応トランスポート
- child_processやstdioによるMCPサーバー起動への依存
- ファイルシステム、ローカルSQLite、ネイティブモジュールへの依存
- Node.js固有の暗号処理・通信APIへの依存
- バンドルサイズ、メモリ、CPU時間、サブリクエストなどの制限
- モジュール初期化時の処理とリクエスト単位の処理の分離
- シークレットや設定をWorkers Bindingsから渡す方法

特に、sera-mcpがstdio前提の場合は、
Workers上で子プロセスとして起動する設計を前提にしないでください。

以下の候補について、実装上成立するかを比較してください。

A. sera-mcpのツール実装を再利用し、Workers上でMCPのHTTPエンドポイントを提供する
B. 公開されたリモートMCPを利用する
C. Seraの処理をアダプター化し、Strandsのツールから直接呼び出す

Bは、実在するエンドポイント、認証、利用条件を確認してください。
Cは、MCP通信を使わない構成になることと、
sera-mcpの再利用範囲を明示してください。

単一Workerにまとめる案と、API/AgentとMCPを別Workerにする案も比較し、
必要ならService Bindings等の適合性を確認してください。

技術的な不確実性が大きい部分は、
実装初期に行う小さな技術検証と合格条件を定義してください。
型チェックやバンドル成功だけで動作確認済みとせず、
ローカルWorkers環境と実際のデプロイ環境での確認を計画してください。

このターンでは検証コードを実装せず、検証計画を示してください。

## 6. アーキテクチャで決めたいこと

フルサーバーレスとは、アプリ側で常時稼働するサーバーや
コンテナの運用を必要としない構成を指します。
Privy、LLM、RPC、Seraなど外部サービスへの依存は明示してください。

以下について、採用案・理由・制約を示してください。

- PagesからWorkers API、Agent、Seraまでの接続構成
- Pages Functionsを使用するかどうかと、その理由
- PagesとWorkers間のオリジン、CORS、認証
- チャットの応答方式：通常のHTTP、SSE、その他
- ストリーミング中のエラー、切断、再接続の扱い
- LLMの複数回呼び出しやMCP接続のライフサイクル
- リクエスト終了後も継続が必要な処理の扱い
- 取引の送信と、その後の確定待ちをどう分離するか
- 会話履歴、ユーザーとウォレットの対応、取引状態の保存先
- 同時実行時にユーザーの認証情報や署名情報を混在させない方法
- ログ、監視、レート制限、入力検証

D1、Durable Objects、KV、Queues、Workflowsなどを検討する場合は、
データの整合性、同時実行制御、耐久性、処理時間の要件から選定してください。
すべてを採用する必要はありません。

取引の承認状態や二重実行防止などに、
不適切な整合性モデルのストレージを選ばないでください。
メモリやローカルファイルに永続状態を依存させないでください。

waitUntilなどによる処理継続を、耐久性のあるジョブ実行と同一視せず、
必要な保証に応じて方式を選んでください。

## 7. ウォレットと取引の設計

Privyをどの役割に使うか明確にしてください。
ユーザー認証、ウォレット作成、署名、鍵管理を分けて説明してください。

ブラウザ側での署名とサーバー側での署名を比較し、
このサンプルに適した方式を提案してください。
PrivyのSDKやAPIがWorkersで利用できるかも確認してください。

以下を設計に含めてください。

- 認証ユーザーと操作対象ウォレットの所有関係の検証
- 秘密鍵や認証情報をLLM、ブラウザ配布物、ログへ露出させないこと
- モデルの判断だけでは送金・swapを実行できない制御
- 承認した取引内容と実際に実行する内容の一致
- 見積もりの期限切れや条件変更時の再確認
- 二重クリック、API再試行、同時リクエストによる二重実行の防止
- ブロードキャスト済みだが結果不明の取引の追跡
- 残高不足、ガス不足、署名拒否、外部API障害の扱い

開発・自動テストではテストネットまたはdry-runを第一候補とし、
実際の対応状況を確認してください。
モックによる動作と実ネットワークでの検証を明確に区別してください。

## 9. デプロイと削除

必要な事前設定が済んだ後は、リポジトリのルートから
次のような単一コマンドで操作できることを目標にします。

- pnpm deploy -- --stage dev
- pnpm destroy -- --stage dev

コマンド名・引数は計画で確定してください。

Wranglerを中心に構成し、必要な場合はCloudflare APIを組み合わせてください。
Wranglerだけで全リソースを一括管理・削除できると仮定せず、
各リソースの作成・更新・削除方法を確認してください。

deployは以下を一貫して扱う設計にしてください。

- 必要なコード生成とビルド
- 必要なCloudflareリソースの作成・更新
- Bindingsの設定
- 必要なデータベースマイグレーション
- Workersのデプロイ
- API URLを反映したフロントエンドのビルドとPagesへのデプロイ
- アプリURLと動作確認方法の表示

PagesはCLIによるDirect Uploadを第一候補とし、
Git連携方式との違いや制約を確認してください。

以下を明示してください。

- Cloudflare認証、アカウントID、必要なAPIトークン権限
- Privy、LLM、RPCなど外部サービスの事前設定
- ローカル開発用設定と本番用シークレットの管理
- フロントエンドへ公開してよい設定値と秘密情報の分離
- PagesのURLとPrivyの許可オリジン設定の整合
- dev/prodとPagesのpreview/production環境の対応
- 再実行してもリソースを重複作成しない方法
- 途中で失敗した場合の再実行・復旧方法
- 作成したリソース名・IDと所有範囲の管理

destroyは、WorkersだけでなくPagesプロジェクトや、
追加したデータストア等を含む削除順序を定義してください。

「全リソース削除」の対象は、このアプリが作成・管理する
指定環境のリソースとして定義してください。
共有リソースや別環境のリソースを削除しない設計にしてください。

保持するデータ、ログ、外部サービスの設定、
削除できないオンチェーンのウォレットや取引履歴はREADMEに明記してください。
独自ドメインを必須にせず、標準ドメインで再現できる構成を第一候補としてください。
